# Upstream Procedure: Landing `atorch_ble` in Home Assistant Core

This document describes the mechanical steps to graft the
`atorch_ble` HACS-distributed custom integration into a fork of
`home-assistant/core` and open the upstream PR. It is the
deliverable of ticket #18 — the actual PR submission is a deferred
post-v1 maintainer decision and is explicitly **not** in scope here.

## Overview

`atorch_ble` is built and distributed via HACS as a custom
integration under `custom_components/atorch_ble/`. The locked
project goal is Gold-tier inclusion in HA Core. Because Core has
strict structural conventions (no `version` in `manifest.json`,
codeowners + requirements registry, generated bluetooth/config_flow
indices, brand assets in a sibling repo), the merge is a mechanical
graft + registry-edit + validator-run procedure rather than a
freeform PR. This document captures that procedure so a future
contributor can execute it without re-deriving the steps.

## Prerequisites

- A Home Assistant Core development environment per
  [the Core docs](https://developers.home-assistant.io/docs/development_environment).
  At minimum: a working venv with Core's `requirements.txt`,
  `requirements_test.txt`, and `pre-commit` installed.
- `script.hassfest` passing locally against the integration as
  distributed in this repo (with `version` stripped — see step 3
  below).
- The `atorch-ble==0.1.1` parser library published to PyPI (the
  version pinned by `manifest.json` — v0.1.1 carries the checksum fix;
  see CHANGELOG). The Core requirement must match the manifest exactly.
- A separate fork of `home-assistant/brands` ready for the logo /
  icon PR (see brands section below).

## Step-by-step procedure

### 1. Fork and clone HA Core

```bash
gh repo fork home-assistant/core --clone --remote
cd core
git checkout dev
git pull upstream dev
git checkout -b atorch-ble-integration
```

### 2. Copy the integration into the Core tree

From this repo's root:

```bash
cp -r custom_components/atorch_ble \
      /path/to/core/homeassistant/components/atorch_ble
```

### 3. Strip the `version` field from `manifest.json`

**This is the most easily-missed step.** Core integrations forbid
the `version` field — it is HACS-only metadata. `script.hassfest`
will reject it. The HACS side of this repo
(`custom_components/atorch_ble/manifest.json`) must continue to
carry the field; only the Core-tree copy has it removed.

One-liner (run from the Core checkout root):

```bash
python -c "import json; p='homeassistant/components/atorch_ble/manifest.json'; \
m=json.load(open(p)); m.pop('version', None); \
json.dump(m, open(p, 'w'), indent=2)"
```

Or, equivalent with `jq`:

```bash
jq 'del(.version)' homeassistant/components/atorch_ble/manifest.json \
  > tmp && mv tmp homeassistant/components/atorch_ble/manifest.json
```

### 4. Edit Core registry files

The following files in the Core tree need entries for the
integration. `script.hassfest` regenerates several of them
automatically (`homeassistant/generated/*.py`,
`homeassistant/generated/integrations.json`); you should run it
*after* editing the hand-maintained registries and then commit
hassfest's output.

#### `requirements_all.txt` — add the parser requirement

```
# homeassistant.components.atorch_ble
atorch-ble==0.1.1
```

The file is generated by `script/gen_requirements_all.py` from the
integration manifests. Re-run it to position the entry correctly:

```bash
python -m script.gen_requirements_all
```

#### `requirements_test_all.txt` — same line under the same header

Regenerated by the same `gen_requirements_all` script.

#### `CODEOWNERS`

```
/homeassistant/components/atorch_ble/ @dallanwagz
/tests/components/atorch_ble/ @dallanwagz
```

The handle must match the `codeowners` array in `manifest.json`
(currently `["@dallanwagz"]`). Insert alphabetically.

#### `homeassistant/components/.coveragerc`

List any source files in the integration that are not covered by
tests. After ticket batch-4/01-03 (unit + flow tests), the
intention is full coverage and **no `.coveragerc` entry is
required**. If hassfest's coverage check flags an entry as needed,
add lines of the shape:

```
homeassistant/components/atorch_ble/coordinator.py
homeassistant/components/atorch_ble/sensor.py
```

(Files with 100% coverage are omitted from `.coveragerc`.)

#### Generated files (regenerated by hassfest — do not hand-edit)

- `homeassistant/generated/integrations.json` — Core's brand /
  integration index.
- `homeassistant/generated/config_flows.py` — config-flow index
  (atorch_ble has `config_flow: true` in its manifest).
- `homeassistant/generated/bluetooth.py` — bluetooth-matcher index
  (atorch_ble declares a `bluetooth` block in its manifest).

After editing the hand-maintained registries, run:

```bash
python -m script.hassfest
```

…and commit any changes hassfest makes to the generated files.

### 5. Copy the test suite

```bash
mkdir -p /path/to/core/tests/components/atorch_ble
cp tests/conftest.py /path/to/core/tests/components/atorch_ble/
cp tests/test_*.py /path/to/core/tests/components/atorch_ble/
```

In the destination copies, rewrite imports:

```
from custom_components.atorch_ble  →  from homeassistant.components.atorch_ble
```

A `sed` one-liner (run from the Core checkout root):

```bash
find tests/components/atorch_ble -name '*.py' -exec \
  sed -i.bak 's|from custom_components\.atorch_ble|from homeassistant.components.atorch_ble|g' {} \;
find tests/components/atorch_ble -name '*.bak' -delete
```

### 6. Run Core's validator suite

All commands run from the Core checkout root with the Core venv
activated:

```bash
# Hassfest — schema, manifest, codeowners, requirements, translations
python -m script.hassfest --integration-path homeassistant/components/atorch_ble

# Translations
python -m script.translations develop

# Pre-commit (ruff, formatting, etc.)
pre-commit run --files homeassistant/components/atorch_ble/*.py \
                       tests/components/atorch_ble/*.py

# Strict mypy (Core's mypy.ini is stricter than the custom-component default)
mypy homeassistant/components/atorch_ble/

# Test suite
pytest tests/components/atorch_ble/
```

Every fix surfaced by these validators **must** be made in this
repo's `custom_components/atorch_ble/` source tree (not in the
throwaway Core checkout) so HACS distribution stays in sync. Then
re-copy the integration into the Core tree and re-validate.

### 7. Open the brands-repo PR (separate, must precede Core PR)

Core PR review blocks on missing brand assets. Open a separate PR
to [`home-assistant/brands`](https://github.com/home-assistant/brands)
*before* the Core PR:

- Add `core_integrations/atorch_ble/icon.png` (256×256 PNG,
  transparent background).
- Add `core_integrations/atorch_ble/logo.png` (free aspect, PNG,
  transparent background).
- Follow the brands repo README for exact sizing / colorspace
  requirements.

### 8. Open the Core PR

Push the branch to your fork and open the PR against
`home-assistant/core:dev` using the standard Core integration PR
template. The PR description should link the brands-repo PR.

## Files that must change in the Core PR — checklist

- **NEW** `homeassistant/components/atorch_ble/` — full directory
  copy (with `version` stripped from `manifest.json`).
- **NEW** `tests/components/atorch_ble/` — full test-suite copy
  with rewritten imports.
- **MODIFIED** `requirements_all.txt` — `atorch-ble==0.1.1` under
  `# homeassistant.components.atorch_ble`.
- **MODIFIED** `requirements_test_all.txt` — same line, same
  header.
- **MODIFIED** `CODEOWNERS` — two lines for integration + tests.
- **MODIFIED** `homeassistant/generated/bluetooth.py` —
  regenerated by hassfest.
- **MODIFIED** `homeassistant/generated/config_flows.py` —
  regenerated by hassfest.
- **MODIFIED** `homeassistant/generated/integrations.json` —
  regenerated by hassfest.
- **MODIFIED** `.strict-typing` — add the integration. Strict typing
  is now implemented (`[tool.mypy] strict = true` passes over
  `custom_components/atorch_ble`, `py.typed` ships, quality_scale
  `strict-typing: done`), so the integration can be added to Core's
  `.strict-typing` allowlist and will pass Core's stricter mypy.
- **MODIFIED** `homeassistant/components/.coveragerc` — only if
  hassfest's coverage check flags it; the intent is full coverage
  with no `.coveragerc` entry.

## Dependency compatibility with Core's pinned BLE stack

The parser library `atorch-ble==0.1.1` has **zero runtime
dependencies** — it is pure stdlib. It does not import or pin
`bleak`, `bleak-retry-connector`, or `home-assistant-bluetooth`.
Therefore no transitive-dep conflict with Core's pinned versions of
those packages is possible at the `pip install -r requirements_all.txt`
level. The integration code in this repo uses Core's
`bluetooth_adapters` integration as a dependency (via
`manifest.json`'s `dependencies` field), which transitively pulls
in Core's BLE stack at runtime — there is no parallel version
constraint coming from `atorch-ble`.

## Outstanding hassfest findings (original dry-run 2026-05-19; status reviewed 2026-06-14)

Hassfest was run against an HA Core `dev` checkout
(`/tmp/ha-core`) with the integration grafted in and `version`
stripped from the manifest. Result: **3 categories of errors
surfaced**, all known and fixable. They are *not* fixed by ticket
#18 — #18's deliverable is identification only.

**Status reconciliation (2026-06-14)** — re-checked against the current source:

| Finding | Status now | Where it's fixed |
|---------|-----------|------------------|
| 1 — manifest documentation URL + `issue_tracker` | **Open, by design** | Graft-time only — the HACS manifest is correct as-is; transform the Core-tree copy. |
| 2 — `[QUALITY_SCALE]` Bronze tier | **Open, blocked** | Gated on `brands` (a *Bronze-tier* rule, still `todo`) — see below. Cannot claim Bronze until brand assets ship. This is the critical-path blocker for Core merge. |
| 3 — `[TRANSLATIONS]` extra `description` keys | **✅ Resolved** | `strings.json` and `translations/en.json` already carry 0 `description` keys. Nothing to do. |

### Finding 1 — `[MANIFEST]` documentation URL + extra `issue_tracker` key

```
Invalid manifest:
  Documentation URL does not begin with
    https://www.home-assistant.io/integrations
    for dictionary value @ data['documentation'].
    Got 'https://github.com/dallanwagz/j7c_ha'
  extra keys not allowed @ data['issue_tracker'].
    Got 'https://github.com/dallanwagz/j7c_ha/issues'
```

**Resolution at upstream time:** rewrite `documentation` to
`https://www.home-assistant.io/integrations/atorch_ble` (the URL
that *will* exist once Core docs are added), and drop the
`issue_tracker` key (Core integrations route issues through the
Core repo's issue tracker, not the integration's source repo).
Both fields stay as-is in the HACS-side manifest.

### Finding 2 — `[QUALITY_SCALE]` tier requirement

```
New integrations are required to at least reach the Bronze tier.
```

**Resolution at upstream time:** `quality_scale.yaml` already
exists; hassfest's check additionally requires a `quality_scale`
key in `manifest.json` set to `"bronze"` (or higher) for new
integrations. Add `"quality_scale": "bronze"` to the Core-tree
copy of `manifest.json`. HACS does not require this field.

> **⚠️ Blocked — read before adding the key.** Claiming a tier
> requires every rule **at and below** that tier to be `done`/`exempt`.
> The `brands` rule is **Bronze-tier** and is still `todo` (see
> `quality_scale.yaml`) because brand assets must be submitted to the
> `home-assistant/brands` repo (step 7), which is deferred. Adding
> `"quality_scale": "bronze"` while `brands` is `todo` will fail
> hassfest's quality-scale validation. **Order of operations: ship the
> brands-repo PR → flip `brands` to `done` → then add the manifest
> `quality_scale: bronze` key.** This is the gating sequence for Core
> inclusion; nothing else here unblocks it.

### Finding 3 — `[TRANSLATIONS]` extra `description` keys — ✅ RESOLVED

The original dry-run flagged `description` keys under
`entity.sensor.<name>` (which Core's translation schema rejects —
only `name` is allowed). **This has since been fixed in the source
tree:** both `strings.json` and `translations/en.json` now carry
**0** `description` keys (verified 2026-06-14). No action remains;
the graft copies clean translation files. If those descriptions are
wanted for users, they belong on the integration's documentation
page (separate PR to `home-assistant/home-assistant.io`), not in the
translation schema.

## What's not in scope (deferred)

- **Opening the actual Core PR.** This is a post-v1 maintainer
  decision.
- **Opening the brands-repo PR for logo / icon assets.** The
  procedure is documented above; the submission is deferred.
- **Submitting `atorch_ble` to the HACS default-repo list.** That
  is a separate distribution path; covered by ticket
  batch-4/04-hacs-distribution-metadata.
- **Removing `custom_components/atorch_ble/` from this repo after
  a hypothetical Core merge.** Open question for the maintainer;
  flagged here so it is not forgotten.
- ~~`.strict-typing` inclusion (Platinum-tier reach item).~~
  **Done** — strict typing is implemented and passing; add the
  integration to Core's `.strict-typing` allowlist at graft time
  (see the checklist above).
- **Backporting fixes to Core stable branches.** Out of scope; the
  validation runs against `dev` only.
